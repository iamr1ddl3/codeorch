Someone sends a spec to the API:

Write a Python function clamp(x, low, high). Include 2 pytest tests.

The Orchestrator gives the request a run_id. From here on, every agent's output is stored under that id.

✦
KEY IDEAThe Orchestrator doesn't write any code itself. It decides which agent runs next, and what to do when something goes wrong.

Sonnet turns the sentence into a structured plan: the function signature, the edge cases (what if low > high?), and the two tests to write.

The plan is not passed to the next agent in memory. It's written to the context store as a row in Postgres.

✦
KEY IDEAAgents keep no state of their own. Each one reads its inputs from the store and writes its output back. If the process dies, the work done so far is still in the database.

Both agents start from the plan and run in parallel with asyncio.gather.

The Tester writes tests from the plan without seeing the Coder's code. If it wrote tests by reading the code, the tests would pass even when the code was wrong.

✦
KEY IDEAThe tests act as an independent check: two agents with different jobs, working from the same spec.

About 7 seconds later, the code and the tests each become a row. The store now has the plan, the code and the tests, which is everything the next stage needs.

The dashboard counts a run with any of these rows missing as context loss, one of its 8 SLIs (target < 2%).

WHAT CHANGED
+Rows: code, tests
~Elapsed ≈2s → ≈9s (both ran at once)

Haiku reads the plan, the code and the tests, then returns a score from 0 to 1 and a list of issues.

≥ 0.75pass → Reviewer
0.50–0.74retry → Coder, with the issues
< 0.50escalate → Orchestrator

This run scores 0.68, so it's a retry. The gate's issue: "no handling when low > high".

✦
KEY IDEAThe model can contradict itself (score 0.92, verdict "retry"). The code ignores the model's verdict and routes on the score alone, so routing stays predictable.

Only the Coder runs again. It gets its best attempt so far plus the gate's issues. The Tester's tests are reused because the plan hasn't changed.

The new attempt scores 0.88, which is a pass.

✦
KEY IDEAThe loop stops early if a retry doesn't improve the score, and it always keeps the best-scoring attempt. Two retries is the hard limit.
WHAT CHANGED

~Gate score 0.68 → 0.88

Reviewer (Sonnet) makes a final check and approves the code. Documenter (Haiku) adds docstrings. The Orchestrator writes a one-line summary and returns the result.

Neither stage can block delivery. If the reviewer fails, the code goes through marked approved=false. If the documenter fails, you get the code without the added docs.

✦
KEY IDEAYou always get something back: documented code, reviewed code, or the raw code files, in that order of preference.

Same run, but this time the Coder times out.

Because of return_exceptions=True, the Tester keeps going and saves its tests. The Coder writes a row with status='failure' and the error. The Orchestrator records its own failure and stops the run.

✦
KEY IDEAOne agent failing doesn't take the others down, and every partial result is a row you can look up. Debugging after the fact is a SELECT, not hours of reading logs.

The gate's model was picked by test, not by guess. RouterBench replayed 13 runs through three gate variants. Haiku returning only a verdict was 3.9× faster and 56% cheaper than the original weighted-rubric gate, with no loss in score.

One spec, seven agents, one store:

  • Agents keep no state and share work only through the store.
  • Tests are written from the plan, so they check the code independently.
  • A cheap model grades the work; the score decides pass, retry or escalate.
  • Retries re-run only the Coder, keep the best attempt, and stop when the score stops improving.
  • Crashes leave rows behind, not gaps.
